# Project Scaffolding

Struttura obbligatoria per `src/`. Vincolante per codice nuovo e per qualsiasi refactor che tocchi la gerarchia.

## Schema

Notazione: `[a | b | c]` = ogni figlio è una di queste opzioni.

```
src/                = [ components/ | hooks/ | features/<feature>/ | index.ts ]
features/<feature>/ = [ components/ | hooks/ | <XxxPage>/ | index.ts ]
<XxxPage>/          = [ components/ | hooks/ | <XxxPage>.tsx | index.ts ]
components/         = [ <ComponentName>/ | index.ts ]
hooks/              = [ useXxx.ts | useXxx/ | index.ts ]
```

`components/` e `hooks/` sono sorelle opzionali a tre livelli (app / feature / page) e contengono solo entry flat. Tutto il resto del repo è ricavabile dall'esempio sotto.

## Esempio annotato

```
src/
├── index.ts                         # esporta SOLO features
└── features/transfers/
    ├── components/
    │   ├── AmountInput/             # entry flat (folder)
    │   │   ├── AmountInput.tsx
    │   │   └── index.ts             # esporta SOLO AmountInput
    │   ├── BeneficiaryCard/
    │   └── index.ts                 # esporta TUTTI i components feature-level
    ├── hooks/
    │   ├── useTransferAmount.ts     # entry flat (file)
    │   ├── useTransferForm/         # entry flat (folder, hook multi-file)
    │   │   ├── useTransferForm.ts
    │   │   ├── useTransferForm.schema.ts
    │   │   └── index.ts
    │   └── index.ts                 # esporta TUTTI gli hooks feature-level
    ├── index.ts                     # esporta SOLO le pagine
    ├── TransferListPage/
    │   ├── components/              # solo entry locali alla list (flat)
    │   ├── hooks/
    │   ├── TransferListPage.tsx
    │   └── index.ts                 # esporta SOLO TransferListPage
    └── TransferCreatePage/          # pagina semplice: niente components/hooks locali
        ├── TransferCreatePage.tsx
        └── index.ts
```

## Regole

1. **Flat** — nessuna entry di `components/` o `hooks/` può contenere a sua volta `components/` o `hooks/`. Sub-componenti o sub-hook salgono come fratelli flat nello stesso `components/`/`hooks/` (page o feature) accanto al padre.
2. **Promozione** — entry usata da 2+ consumer dello stesso livello sale al livello superiore: page → feature → app. Import che attraversa pagine (`../../OtherPage/components/X`) = segnale di promozione mancata.
3. **Barrel puri** — i tre `index.ts` "verticali" (`src/`, `<feature>/`, `<Page>/`) sono sempre presenti e esportano solo features / pagine / la pagina. I barrel di `components/`/`hooks/` esistono solo se la folder esiste e ri-esportano tutto il loro contenuto. Import sempre via barrel (`from "../components"`, o tra fratelli flat `from ".."`/`from "../Bar"`), mai bucati (`from "../components/Foo/Foo"`).

Folder `components/`/`hooks/` si creano **solo** quando hanno almeno un'entry — niente folder vuote né barrel orfani. Niente `utils/` paralleli.

## Stato corrente del repo

La nuova struttura si applica a:

- codice nuovo (features create da zero)
- refactor **esplicitamente richiesti** dall'utente

**Non riorganizzare features esistenti senza richiesta esplicita.** Quando lavori su un file dentro una struttura legacy, mantieni le convenzioni della folder e non promuovere il refactor di tua iniziativa.
